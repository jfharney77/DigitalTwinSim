# DigitalTwinSim

Hardware digital twins: one directory per simulated component, each a pure-engine
FastAPI backend and a React/Vite frontend in the Dell clean-design skin. The
shared skeleton lives in [`twinkit/`](twinkit) (models, reading levels, the app
factory, the trace invariants) and [`packages/twin-ui/`](packages/twin-ui) (the
design tokens and the shell components).

Start any component without reading its README:

```bash
scripts/dev.sh --list          # every component, its ports and its status
scripts/dev.sh DellPowerMax    # backend on :8005, frontend on :5178
pytest                         # every component's suite, from the repo root
```

## Learn the twins as one course

[`Learn/`](Learn) puts the twins in a teaching order: twelve modules from the
GPU roofline to an AI-factory capstone, plus electives, each with a question to
answer before pressing play and a link to the twin step that settles it. Run
`./Learn/scripts/serve.sh` and open `http://localhost:5172/Learn/`; every link
and quoted number is pinned by `pytest Learn`. See [`Learn/README.md`](Learn/README.md).

Ten narrative twins also serve one failure trace each beside the happy path
(`#scenario=<id>`: a gray link that reads green, a clean that returns less than
it promised, a node that dies under load, and so on). The course teaches each as
a "When it goes wrong" stop and strings them into a "What goes wrong" track; the
twin, scenario id and invariant are tabled under "Failure scenarios" in
[`CLAUDE.md`](CLAUDE.md).

Interactive web app that draws the inner structure of a GPU and animates how a
matrix multiplication executes across it. Teaching/visualization tool — see
[`initial_spec.md`](initial_spec.md) for the full design and roadmap.

## Static hosting — the whole thing as files

Everything here runs with no backend: `scripts/build_site.sh` assembles `site/`
(gitignored) from the root index, `Learn/`, `CustomerSetup/` and every
static-ready twin, and GitLab Pages (`pages` in `.gitlab-ci.yml`, plus a manual
`pages-preview` on branches) or GitHub Pages (`.github/workflows/pages.yml`)
publishes it.

    scripts/build_site.sh                  # all of it, into site/
    scripts/build_site.sh DellPowerStore   # one twin, plus the static pages
    scripts/smoke_static.sh <Component>    # the component's own smoke manifest, no backend

A twin's `GET` routes become JSON snapshots at build time, the guided scenarios'
`POST` bodies are prebaked, and anything else — a scenario you build yourself in
a physics app, a lab you ask it to grade — runs **the component's real
`engine.py` in the browser** under Pyodide, so a static page is not a reduced
one. The recipe per component, what is genuinely lost (GPU's live CUDA tab needs
SSE and a session store, so it replays shipped recordings and says so) and every
gotcha are in [`docs/STATIC_HOSTING.md`](docs/STATIC_HOSTING.md).

## Labs — the graded half of the course

A guided scenario sets the dials and narrates; a **lab** hands you a goal and
its constraints, you build the scenario with the app's own controls, and a pure
scoring function grades the trace. Sixteen apps carry three labs each at rising
difficulty, and two rules keep them honest: delivered work is always a
criterion (an idle machine never passes) and every stated constraint is measured
from the trace rather than taken on trust. Open an app's **Labs** tab, or
`#lab=<id>` directly.

The course links one lab per module that has one, and its **Labs** track visits
just those stops. Pattern and pilot: [`docs/LAB_PATTERN.md`](docs/LAB_PATTERN.md).
Grading is data-only (`GET /api/labs` plus the metrics), so the hosted site
grades in the browser exactly as the backend does.

## compose/ — two engines at once

The twins have always cross-referenced each other in prose. [`compose/`](compose)
makes the carry a piece of code with a test on it: **one engine's trace becomes
another engine's scenario, and an identity is asserted across the seam** — rack
heat into the CDU's load, the CDU's cap back into the rack (a fixed point, run to
convergence), storage delivery into the GPUs' data feed, a gray link into lost
tokens. A coupling with no identity is a prose cross-reference with extra steps
and is not admitted. Nine preset chains, a Couplings page on :5221, and the
capstone module of the course ends there. Design:
[`docs/COMPOSITION_DESIGN.md`](docs/COMPOSITION_DESIGN.md).

## The GPU twin

The rest of this file describes `GPU/`, the reference implementation.

### Architecture

A Python/FastAPI backend owns the **deterministic simulation engine**; the React
frontend fetches the full `SimState[]` trace and animates it on its own clock
(the UI owns the clock — a core spec invariant).

```
backend/   FastAPI + pure engine
  app/
    models.py    GpuProfile, Workload, SimState (pydantic; camelCase JSON)
    profiles.py  default dies (Generic-128, Generic-512, RTX-4060-Laptop)
    mapping.py   output cell -> physical core (round-robin)
    engine.py    pure simulate(profile, workload) -> SimState[]
    main.py      FastAPI: /api/health, /api/profiles, /api/simulate
  tests/         trace-based invariant tests (spec §8)

frontend/  React + Vite + TypeScript
  src/
    api.ts            fetch profiles + trace
    types.ts          mirrors backend models
    components/       DieView (SVG), Controls, Counters, Legend
    App.tsx           composition root; owns the playback clock

scripts/   start_backend.sh, start_frontend.sh, start_all.sh, stop_all.sh
```

Data flow: `Controls → POST /api/simulate → trace: SimState[] → DieView`.

### Run it

```bash
./scripts/start_all.sh      # backend (background) + frontend (foreground)
# or individually:
./scripts/start_backend.sh  # FastAPI on :8000
./scripts/start_frontend.sh # Vite dev server on :5173
./scripts/stop_all.sh       # stop both
```

Open http://localhost:5173. The Vite dev server proxies `/api` to the backend on
:8000.

## Live CUDA co-browsing

The third tab (`#live`) shows real CUDA activity on this machine's RTX 4060
Laptop GPU: instrumented lessons (`GPU/cuda/lessons/`, `make run-NN` or
`make watch-NN`) light the SMs the hardware scheduler actually chose; a
per-SM Gantt shows block residency; shift-click two timeline chips to
compare runs; "▶ Guided lessons" plays the narrated, GPU-free tour. Capture
tiers: `twinprobe.cuh` (placement + timing), `twin-sampler` (telemetry;
`--once` for scripts), `twin-run <any-cuda-app>` (CUPTI, timing-only).
Recordings are replayable, downloadable, and deletable;
`scripts/prune_sessions.sh` clears ad-hoc ones.

API (events from `cuda/twinprobe.cuh` and `cuda/twin-sampler`):

- `POST /api/live/ingest` `ProbeEvent` → `LiveState` (auto-starts an ad-hoc session; 409 past the 100k-event cap)
- `GET  /api/live/stream` → Server-Sent Events of `LiveState`; `GET /api/live/latest` → the current frame, SSE-free
- `POST /api/live/session` / `DELETE /api/live/session` — start/stop a named recording
- `GET  /api/live/sessions?limit=N` (newest first) → `SessionInfo[]`; per session: `/trace` (replayed frames), `/summary` (kernel stats), `/download` (raw JSONL), `/events.csv`, `DELETE` (409 while recording), `PATCH {name}` (rename)
- `POST /api/live/import` `{name, jsonl}` — save an uploaded recording (validated by full replay first)
- `GET  /api/measurements` → latest calibration per metric, with history
- `GET  /api/tour` + `/api/tour/recordings/{lessonId}` — the guided lessons (deep link: `#live/tour`)

Replay keyboard shortcuts: **space** pauses/resumes, **←/→** step the cursor;
speed buttons 0.5×–4×. No GPU? `./scripts/demo_feed.py` replays a golden
lesson recording through real ingest so the whole Live tab works untouched.

The original single-file reference implementation is preserved as
[`gpu-sim.html`](gpu-sim.html) (open directly in a browser) and serves as the
behavior oracle.
